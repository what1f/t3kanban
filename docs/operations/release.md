# Release Checklist

> For maintainers. Using T3 Kanban? See [Install](../user/install.md).

T3 Kanban publishes installable desktop packages from one Git tag. The release workflow is
intentionally limited to this fork's desktop distribution; it does not publish the upstream `t3`
npm package, deploy hosted services, or create nightly builds.

## Release targets

[`.github/workflows/release.yml`](../../.github/workflows/release.yml) runs when a tag matching
`v*.*.*` is pushed. It builds these packages on their matching GitHub-hosted runner:

- macOS Apple Silicon (`arm64`): DMG and ZIP
- Windows (`x64`): NSIS installer
- Linux (`x64`): AppImage

The Windows package includes a Linux `node-pty` binary for its WSL backend. The release is created
only after all three platform builds succeed, so users never see a partial release. Installer
metadata, differential-update blockmaps, and `SHA256SUMS.txt` are uploaded with the packages.

## Signing status

Current packages are unsigned:

- macOS is not signed with an Apple Developer ID or notarized. Gatekeeper may require the user to
  remove the quarantine attribute as documented in the install guide.
- Windows is not Authenticode-signed. SmartScreen may warn before first launch.
- Linux AppImages are not GPG-signed; users can verify the published SHA-256 checksum.

No signing secrets are required for the current workflow. Add signing only as a separate change
after the corresponding certificates and CI credentials are available.

## Publish a release

1. Confirm `main` contains the exact commit to release and its CI run is green.
2. Choose a version that does not already exist in the fork, such as `v0.1.1`.
3. Create and push an annotated tag:

   ```bash
   git switch main
   git pull --ff-only
   git tag -a v0.1.1 -m "T3 Kanban v0.1.1"
   git push origin v0.1.1
   ```

4. Open the repository's Actions page and watch the **Release** workflow.
5. When it succeeds, open GitHub Releases and confirm all three platform installers and
   `SHA256SUMS.txt` are present.
6. Download and smoke-test each package on its target operating system before announcing it.

Tags with a suffix, such as `v0.1.0-beta.1`, are published as prereleases. Plain semantic versions,
such as `v0.1.0`, are marked as the latest release.

## Expected assets

For `v0.1.1`, the release should include at least:

```text
T3-Kanban-0.1.1-arm64.dmg
T3-Kanban-0.1.1-arm64.zip
T3-Kanban-0.1.1-x86_64.AppImage
T3-Kanban-0.1.1-x64.exe
SHA256SUMS.txt
```

The workflow also publishes platform update manifests and `.blockmap` files generated by the
existing desktop artifact builder.

## Troubleshooting

- **No workflow starts:** confirm the workflow file is on the tagged commit and the pushed tag
  matches `v*.*.*`.
- **The release job is skipped:** one of the platform builds failed. Fix or rerun that job; do not
  manually publish a partial set of packages.
- **Linux icon generation fails:** confirm the ImageMagick installation step succeeded.
- **Windows WSL packaging fails:** inspect the separate `Build WSL node-pty` job and confirm its
  artifact was downloaded by the Windows build.
- **macOS packaging produces no files:** rerun the failed job with verbose logs retained. The
  supported builder is `scripts/build-desktop-artifact.ts`; do not replace it with a second
  Electron Builder configuration.
